APP-REL-011 — PRODUCTION PUBLISHING HEALTH-PROBE DIAGNOSIS AND REDEPLOYMENT

ROLE
You are operating as the deployment-boundary investigator for APP-REL-011.

OBJECTIVE
Diagnose the reported Replit Publishing production failure:

    /healthcheck -> HTTP 500

and, if and only if the evidence identifies a Replit Publishing/deployment
configuration problem, correct that deployment configuration and redeploy the
current production code.

IMPORTANT AUTHORITY BOUNDARY
Do NOT modify application source code merely to make an undocumented
/healthcheck probe pass.

Do NOT:
- modify server/index.ts;
- add /healthcheck;
- change /health;
- modify APP-REL-011 application scope;
- modify RELEASE-CONTRACT.json;
- modify WORK-CYCLE-AUTHORITY.json;
- manually change verification.status from PENDING;
- bypass or weaken any release guard;
- change deployment target, build command, or run command unless the actual
  Replit Publishing configuration is demonstrably inconsistent with the
  repository release contract.

KNOWN REPOSITORY FACTS
- Production deployment target: autoscale.
- Production build: npm run build.
- Production run: npm run start.
- npm start resolves to:
    NODE_ENV=production node dist/index.js
- Production server binds to 0.0.0.0:$PORT.
- The application owns:
    GET /health
    HEAD /health
- Repository-wide search found no application/deployment declaration of
  /healthcheck.
- The production build's serveStatic() serves dist/public and has an SPA
  fallback.
- The repository therefore does NOT establish /healthcheck as the canonical
  application health endpoint.
- The reported /healthcheck HTTP 500 is consequently currently classified as
  a deployment/platform probe issue, pending direct Replit Publishing
  evidence.

RELEASE CONTRACT
The canonical deployment contract requires:
- deploymentTarget = autoscale
- build = ["npm", "run", "build"]
- run = ["npm", "run", "start"]
- production port mapping = local 5000 -> external 80
- no deployment PORT override

TASK — PHASE 1: INSPECT REPLIT PUBLISHING

Inspect the actual Replit Publishing deployment configuration and determine:

1. What health-check/probe path is configured, if any.
2. HTTP method used by the probe.
3. Expected status code.
4. Actual failing request/response.
5. Whether /healthcheck is a Replit-generated/default probe or an explicitly
   configured application probe.
6. Which deployment revision is currently published.
7. Whether the published revision corresponds to the current repository HEAD.
8. Whether the deployment is actually using:
       npm run build
       npm run start
   with the expected autoscale configuration.
9. Whether any deployment-specific environment/configuration is causing the
   probe to receive HTTP 500.

TASK — PHASE 2: REPRODUCE THE FAILURE AT THE DEPLOYMENT BOUNDARY

Use the actual published production deployment, not the development workflow.

Test the configured health probe exactly as Replit Publishing tests it.

Also test:

    GET /health
    HEAD /health

Record status codes and concise response information.

Do NOT treat a successful local development-server response as proof that
the published deployment is healthy.

TASK — PHASE 3: DECISION

If the evidence shows that Replit Publishing is using an incorrect,
stale, missing, or otherwise inconsistent health-probe configuration:

- correct ONLY the Replit Publishing/deployment configuration;
- preserve the repository's canonical application health endpoint;
- preserve the Release Contract;
- preserve WORK-CYCLE-AUTHORITY;
- do not manually alter verification status.

If the evidence instead shows that the published application itself returns
500 for the canonical /health endpoint:

STOP before modifying application code.

Report the exact production failure, including the relevant runtime error,
environment/configuration cause, and deployment revision.

Do not guess at a fix.

TASK — PHASE 4: REDEPLOY

If and only if Phase 3 identifies a deployment-boundary configuration defect
that can be safely corrected:

1. apply the minimal deployment configuration correction;
2. publish/redeploy the current production revision;
3. wait for deployment completion;
4. verify the deployed revision;
5. test the configured health probe;
6. test GET /health;
7. test HEAD /health.

Do not deploy a different code revision.

TASK — PHASE 5: FINAL EVIDENCE

Return a concise evidence report containing exactly:

If the probe failure cannot be resolved without an application-code change,
state:

    DEPLOYMENT_BOUNDARY_RESOLUTION=NOT_POSSIBLE

and stop.

Do not modify WORK-CYCLE-AUTHORITY.json or manually transition its
verification status.

SUCCESS CONDITION

The task is successful only if the current production revision is deployed
and the actual Replit Publishing health probe succeeds, OR if the evidence
proves that the remaining failure is outside the repository/deployment
configuration authority and cannot safely be corrected by this task.
